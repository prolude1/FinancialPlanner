# Setup and operation

## Initial configuration

Start Docker Desktop. If `.env` already exists, Docker Compose reads it automatically: run `docker compose up` and use the dashboard password recorded in the file. Generated local defaults use port 8080, Asia/Singapore, and a 15-minute market refresh; Telegram stays idle until its token and owner ID are entered.

For a fresh configuration when `.env` does not exist, run:

```sh
python3 scripts/configure.py
docker compose up
```

The setup script uses Python's standard library only. It creates `.env` with mode `0600`, refuses to overwrite existing settings, generates database/session/service secrets, and stores a PBKDF2-SHA256 hash of your chosen web password. No virtual environment is required. Keep `.env` private; it is ignored by Git and excluded from Docker build context.

Open `http://localhost:8080`. Use `localhost`, not a LAN address or `127.0.0.1`, for the browser: mutation requests validate the configured origin. Change `WEB_PORT` before startup if 8080 is occupied, then visit `http://localhost:YOUR_PORT`.

`docker compose up` builds missing local images, starts PostgreSQL, waits for database health, runs schema setup, and starts the API, web, worker, and bot. The database is not exposed on a host port. Use `docker compose up -d` for background operation and `docker compose up --build -d` after code changes.

## Telegram setup

1. In Telegram, open the official [@BotFather](https://t.me/BotFather), create a bot using `/newbot`, and keep the returned token private.
2. Obtain your numeric Telegram user ID from a message you send to your bot: before starting its polling service, send `/start`, call the official Bot API `getUpdates` locally, and inspect `message.from.id` and the private `message.chat.id`. Avoid pasting the token into shared terminals or browser history. The helper below performs this lookup without printing the token.
3. Set `TELEGRAM_BOT_TOKEN` and `TELEGRAM_OWNER_ID` in `.env`, or enter them in the configuration script.
4. Recreate the bot using `docker compose up -d --force-recreate bot`.
5. Send `/start`, then `/account_add` in your private conversation with the bot.

Owner lookup helper (stop the bot first so it does not consume the update):

```sh
docker compose stop bot
docker compose run --rm --no-deps bot python -m app.identify_owner
```

The helper reads the configured token, polls once, and prints numeric sender/chat IDs from private messages. Select your own message's ID; it does not automatically authorize anyone. Then update `.env` and start the bot. Telegram instructions and update fields follow the [official Bot API](https://core.telegram.org/bots/api#getupdates).

With a blank token or owner ID, the bot stays idle. With credentials present, both the sender ID and private chat ID must match. Group chats and other users receive no account data. There is no public webhook.

## Configuration reference

| Setting | Use |
|---|---|
| `POSTGRES_PASSWORD` | Random hex database password generated by setup |
| `SESSION_SECRET` | At least 32 random characters; signs local login sessions |
| `BOT_API_SECRET` | Private credential for bot-to-API calls |
| `WEB_PASSWORD_HASH` | `salt_hex:hash_hex`, PBKDF2-SHA256 with 600,000 iterations |
| `TELEGRAM_BOT_TOKEN` | Token from BotFather; blank disables bot activity |
| `TELEGRAM_OWNER_ID` | Your positive numeric Telegram user ID |
| `TELEGRAM_BOT_USERNAME` | Public bot username, without `@`; used to build the link challenge deep URL |
| `KEYCLOAK_ISSUER` | Exact realm issuer; local default is `http://localhost:8081/realms/financial-planner` |
| `KEYCLOAK_AUDIENCE` | API audience configured in Keycloak access tokens; local default is `financial-planner-api` |
| `KEYCLOAK_JWKS_URL` | Signing-key URL; local default uses the internal `keycloak:8080` Compose endpoint |
| `KEYCLOAK_ORIGIN` | Keycloak origin added to the web CSP; local default is `http://localhost:8081` |
| `KEYCLOAK_REALM` | Public Keycloak realm name; local default is `financial-planner` |
| `KEYCLOAK_WEB_CLIENT_ID` | Public Keycloak SPA client ID; local default is `financial-planner-spa` |
| `.env.telegram-link` | Private file generated by setup; contains the distinct bot-only Telegram-link confirmation secret |
| `.env.keycloak` | Private file generated by setup; contains the Keycloak database role password |
| `WEB_PORT` | Local web port, default 8080 |
| `APP_TIMEZONE` | Transaction date defaults; `Asia/Singapore` initially |
| `MARKET_POLL_SECONDS` | Price/FX worker interval, default 900, minimum 60 |
| `STOCK_PRICE_PROVIDER` | Stock/ETF quote provider selected by the provider factory; default `yahoo` |

## Local Keycloak setup

The local stack runs Keycloak `26.7.4` against the existing `keycloak` database on the existing PostgreSQL container. It does not create a second PostgreSQL server or initialize a new realm. The Compose mapping binds Keycloak only to `127.0.0.1:8081`; it uses `start-dev` for local use and is not internet-ready or production-hardened. Keep `.env.keycloak` private (mode `600`); it supplies the dedicated `keycloak_app` database password. Back up the `keycloak` database before changing the Keycloak image version.

After Keycloak starts, open `http://localhost:8081/admin/` and sign in with the existing master-realm admin account. In the existing `financial-planner` realm, create a separate public OIDC client named `financial-planner-spa`: enable Standard Flow, disable client authentication, implicit flow, and direct access grants, and require PKCE method `S256`. Register exactly these two redirect URIs: `http://localhost:8080/` for the dashboard and `http://localhost:8080/telegram-link.html` for Telegram linking. Set the exact web origin to `http://localhost:8080`. Add an access-token audience mapper whose audience is exactly `financial-planner-api`. Leave self-registration disabled; create invite-only users manually through the realm's Users screen and set a temporary password that they must change at first sign-in.

The SPA settings default to issuer `http://localhost:8081/realms/financial-planner`, realm `financial-planner`, and client ID `financial-planner-spa`. The API fetches signing keys over the private Compose network at `http://keycloak:8080/...`; the token issuer remains the browser-facing loopback URL. Keycloak bearer tokens now select a principal-scoped ledger for financial API routes. A first authenticated request creates an empty ledger; it does not automatically receive the existing data. The existing ledger remains unassigned until a trusted local operator issues a one-time claim code and the intended owner redeems it after signing in. Once claimed, old local-password sessions and the legacy singleton bot cannot read or change it. Do not expose port 8081 publicly or use these `start-dev` settings for internet deployment.

To make the existing ledger available to its owner, first ensure the intended Keycloak user exists. Have that owner claim before creating financial records in the new tenant; a tenant with financial data or portfolio history is never overwritten by a claim (a pristine empty tenant created by sign-in is okay). From the trusted operator shell, run `docker compose exec api python scripts/issue_legacy_claim.py`; deliver the one-time code out-of-band, then submit it from the signed-in user's claim screen (backend: `POST /api/owner-claim`, JSON `{\"code\":\"...\"}`). It expires after ten minutes and can be redeemed once. Do not put the code in a URL, shell argument, log, or browser storage. The claim moves the legacy ledger and its derived portfolio history atomically to that verified Keycloak principal; it does not give other users access. Keep the pre-change PostgreSQL dump until migration and data checks are complete.

Linked Telegram financial access requires a distinct `BOT_API_SECRET` for internal service authentication and a Telegram↔Keycloak link. The bot calls `POST /internal/bot/financial/dashboard` or `/internal/bot/financial/command/{command}` with the sender and private-chat IDs; the backend maps the linked sender to its principal. Persistent guided-flow/reply state is keyed per linked sender, while the update polling offset remains one global bot runtime value. An unlinked sender receives 403 and never falls back to the legacy ledger.

The claim issuer is included in the backend image; rebuild/recreate the API after updating the image before running it.

Internal database URL and web origin are composed by Compose. Never change a populated volume's database password only in `.env`; PostgreSQL initialization variables do not reset an existing database user's password.

`scripts/configure.py` creates separate mode-600 `.env.keycloak` and `.env.telegram-link` files. Keep the issuer and JWKS endpoint operator-controlled. The issuer must use HTTPS except for loopback development; JWKS must use HTTPS except for the exact internal Docker URL `http://keycloak:8080/...`. Link challenge creation stays unavailable until the bot username and separate link secret are valid.

The web container serves `/runtime-config.js` at startup from `KEYCLOAK_ISSUER`, `KEYCLOAK_REALM`, and `KEYCLOAK_WEB_CLIENT_ID`. These are public browser settings, not secrets. Set `KEYCLOAK_ORIGIN` to the matching origin, for example `https://login.example.com`, so the Content Security Policy allows that Keycloak origin in `connect-src`. Keep issuer, realm, and origin aligned; the issuer must be the exact discovery issuer URL, typically `https://login.example.com/realms/financial-planner`. The SPA expects a public client named/configured for the web origin, with Standard Flow enabled, implicit and direct grants disabled, and PKCE S256. Register both exact redirect URIs `<web-origin>/` and `<web-origin>/telegram-link.html`, plus the exact web origin. Configure an API audience mapper so access tokens include the `KEYCLOAK_AUDIENCE` value. Recreate the web container after changing these settings.

The dashboard root and Telegram-link page are separate static entry points. Both use the pinned Keycloak JavaScript adapter and keep tokens in memory. They send access tokens as Bearer credentials and do not rely on the old password session. The dashboard makes principal-scoped financial requests; the Telegram page manages the user-scoped Telegram connection without loading the dashboard bundle. The old password-login routes remain only as a legacy compatibility path and cannot access a ledger after that ledger is claimed.

## Normal operation

```sh
docker compose ps
docker compose logs --tail=100 api bot worker
docker compose down
```

Normal `down` preserves the database volume. Do not add `-v` to a normal shutdown: that deletes the volume. Laptop sleep stops responsiveness; services reconnect when available. The worker refreshes completed-session data on startup and then periodically.

The dashboard shows connection state, price dates, missing valuations, and provider failures. Data lacking a price/rate is excluded from aggregates with an explicit incomplete-total warning. Broker quantities and native cash remain visible.

Telegram conversations expire after 30 minutes, survive ordinary process restarts, and require `/confirm` before saving. Updates are deduplicated. Pending replies are retained for retry; a reply may appear twice after an interrupted delivery, but the same confirmed update cannot double-post a trade. Check `/history` if delivery is uncertain.

## Backup

```sh
sh scripts/backup.sh
```

This creates a PostgreSQL custom-format dump in `backups/` with private filesystem permissions. It includes accounts, transactions, loan terms, audit receipts, bot conversation state, and cached valuations. Copy backups to separate storage. Keep `.env` separately; database backups do not contain deployment secrets.

The signed-in dashboard also provides **Export data** and **Import data**. Export produces a readable `.xlsx` workbook with six sheets: `Metadata`, `Planner State`, `Instrument Catalog`, `Portfolio History`, `Stock Cache`, and `Stock Cache Data`. For authenticated tenant backups, the workbook contains only that tenant's ledger and derived history; shared market catalog/cache sheets are empty and ignored on import. The former template/legacy format retains all six sheets for compatibility. Nested state uses typed-node rows, so keys, list positions, nulls, booleans, and exact decimal strings can be restored without embedded JSON blobs. Keep downloaded workbooks private because they contain financial data.

Import accepts only the six-sheet XLSX workbook format (format version 1, schema version 1), up to 64 MiB uploaded and 200 MiB expanded. Validation rejects formulas, external links, hidden sheets, macros, and unsupported workbook structures, checks row counts/checksums, then presents a preview before explicit confirmation. The downloadable template is a synthetic sample workbook; its preview warns that importing it replaces current records. A confirmation expires after ten minutes and is bound to the authenticated principal. Tenant imports replace only that tenant's ledger and history; they do not modify the shared catalog, shared quote cache, another tenant, or global Telegram polling state.

Before replacement, the API writes a private rollback workbook to the persistent `planner-import-rollback` Docker volume, mounted at `/data/data-import-rollback/`. Each successful import creates a unique mode 0600 `.xlsx` snapshot of all four prior application tables. The volume retains the ten most recent snapshots and prunes older ones after a later import commits. This is a recovery aid, not an archival backup. Keep regular `scripts/backup.sh` dumps and downloaded exports separately. The web sign-in cookie and deployment secrets are outside the workbook and remain unchanged by import.

## Restore into a separate database first

Substitute the actual dump path below. These commands create a new database rather than overwriting the running one:

```sh
docker compose exec -T db createdb -U planner planner_restore
docker compose exec -T db pg_restore -U planner -d planner_restore < backups/planner-YYYYMMDD-HHMMSS.dump
docker compose exec -T db psql -U planner -d planner_restore -c 'SELECT id, schema_version FROM planner_state;'
```

For recovery, stop writers (`docker compose stop api bot worker web`), take a fresh backup of the current database, and switch the database name in the Compose `DATABASE_URL` to the verified restored database. Start the stack and check known account balances and transaction references. Preserve the old database until recovery is verified. Do not delete the volume as a recovery technique.

An exact dump/restore comparison was verified in the isolated test stack. See [validation](validation.md).

## Container-only testing

```sh
docker build -t financial-planner-backend:local -f backend/Dockerfile .
docker run --rm financial-planner-backend:local python -m pytest -q -p no:cacheprovider
docker build -t financial-planner-web:local web
```

`tests/smoke.py` is intentionally restricted to a separately configured, empty `financial-planner-test` Compose stack on port 18080. It creates synthetic accounts. Do not run it against your personal database.
